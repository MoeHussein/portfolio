## 7. Visual system

- Default dark surface: deep charcoal or near black.
- Light surface: warm off-white rather than pure white.
- Accent colors: restrained cyan, violet, and coral derived from approved polarization imagery.
- Display type: clean technical grotesk.
- Body type: highly readable humanist sans serif.
- Monospace: limited to technical metadata and labels.
- Typography must support English, Turkish, and Arabic without fallback inconsistencies.
- Layout relies on spacing, scale, imagery, and hierarchy rather than excessive cards.
- Images use responsive AVIF or WebP derivatives while preserving suitable originals.
- No personal logo is required. A typographic name treatment or restrained MH monogram is sufficient.

## 8. Interaction behavior

- The initial theme is dark unless a previous explicit choice is stored.
- Theme and locale preferences may be stored locally without analytics or tracking.
- Controls use semantic labels, visible focus states, and sufficient target sizes.
- Arabic changes document direction and component alignment rather than only translating strings.
- No automatic carousel, parallax, cursor gimmick, or continuous motion.
- Transitions are short and restrained.
- Reduced-motion preferences disable nonessential transitions.
- Downloads expose document type and language clearly.
- Broken or unavailable optional assets fall back to meaningful text rather than empty frames.
- Missing locale content falls back deliberately to approved English and is flagged during build validation.

## 10. Technical architecture constraints

- Select the framework only after Reference-First live research compares suitable static architectures, including current Astro and Next.js options.
- Use exactly one application shell, router, styling foundation, content system, and deployment model.
- Produce a static GitHub Pages artifact through GitHub Actions.
- Avoid server-only features, authentication, databases, and runtime APIs.
- Keep content structured so a project can be added without redesigning components.
- Use self-hosted or locally bundled fonts where licensing allows.
- Keep third-party runtime scripts out of version one.
- Preserve future custom-domain support.
- Keep external links safe and clearly identifiable.
